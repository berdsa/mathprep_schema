# Delivery Integration Contract

For whoever builds the student-facing delivery layer (Telegram bot, web app, printed-worksheet flow — none exist as a repo yet). This document defines what you integrate *against*; it is not a spec for what you build. **You do not need, and should not request, any change to `taskgen` or `grader` to build a delivery layer against what's described here** — if something here turns out to be genuinely impossible to build against, that's a named blocker to raise, not something to design around silently.

**Provenance note:** this document is written from the system's design contracts as of this pass. `schema/docs/api-contract.md` was separately generated by reading the actual current Go handler code — treat that one as authoritative for exact current error-code behavior, timing values, and any spec-vs-code drift it recorded (it found several: a stale 24-hour expiry mention, undocumented plain-text grader errors, gaps in 403/409/429 behavior). Reconcile the two before relying on fine detail here; this document is the integration-contract framing, that one is the ground truth for exact current behavior.

---

## 1. System map (detail: `schema/docs/srd/03-architecture.md`)

| Service | Owns | You call it for |
|---|---|---|
| `taskgen` | Generates task instances, assigns to students | Requesting and fetching a task set |
| `grader` | Validates submitted answers | Submitting a student's answer, getting a verdict |
| `schema` | Shared DB schema, dictionaries, validation pipeline | Nothing directly — this is infrastructure the other two depend on |

Neither service calls the other directly, and neither calls you — everything here is request/poll, initiated by your side. There is no push/webhook mechanism from the system toward a delivery layer.

## 2. Endpoints

### `POST /v1/generation-requests` — `taskgen`

```json
// request
{ "student_id": "uuid", "grade": 3, "topics": ["G3-NUM-001"], "count": 10, "idempotency_key": "uuid" }
// 202 response
{ "request_id": "uuid", "status": "PENDING" }
```
- `count` capped at ≤50 server-side.
- `idempotency_key` is **required**, not optional — a retry without one is rejected (`400`), and a retry *with* the same `(student_id, idempotency_key)` pair within 24h returns the original `request_id` and its **current** status, not a frozen snapshot of the first response. A `PENDING`→`DONE` change between your first call and a replay is correct behavior, not a bug — don't build retry logic that assumes byte-identical replays.
- If a requested topic/grade combination doesn't currently resolve to an eligible type, you get `422 UNSUPPORTED_TYPE` — the system does not silently substitute a different type for what you asked for.

### `GET /v1/generation-requests/:id` — `taskgen`

```json
// 200 response, once DONE
{
  "request_id": "uuid", "status": "DONE", "task_set_id": "uuid",
  "items": [
    {
      "item_id": "uuid",
      "type_id": "G3-NUM-001",
      "spec_version": "1.0.0-draft",
      "tier": "T1",
      "locale": "ru-KZ",
      "render_target": "plaintext",
      "problem": "257 + 486 = ?",
      "answer_widget": "NUMERIC",
      "widget_config": null
    }
  ]
}
```
- `answer_widget` and `widget_config` are new fields (see §4) — check for their presence before assuming an older contract shape.
- **`items` is an ordered array, and that order is stable.** This is what makes the "printed paper, digital answer entry" flow work: if you print this task set, number the items 1..N in this array order, then your answer-entry screen can show "Задание 1: [answer control]" without re-rendering the problem text at all, correlated purely by position. You don't need a separate "task number" concept — the array index *is* the task number, as long as you don't re-sort it.
- `spec_version` ending in `-draft` means the type is `GATED` (passes automated checks) but not yet `FINAL` (independently curriculum-verified) — informational, not something to branch UI behavior on.
- `render_target` may be `plaintext`, `unicode-math`, or `latex` — if `latex`, the `problem` string is LaTeX source, not literal display text; render it accordingly (see §5 for why the plaintext fallback always exists too).

### `POST /v1/items/:id/submissions` — `grader`

```json
// request
{ "student_id": "uuid", "raw_input": "743", "idempotency_key": "uuid" }
// 200 response (synchronous — every validation method except CAS)
{ "verdict": "CORRECT", "reason_code": "OK", "correct_answer_display": "743", "attempt_index": 1 }
```
`idempotency_key` is required here too, scoped to `(item_id, student_id, idempotency_key)`.

**Exception — the 5 CAS-backed types only** (radical/derivative/integral/ODE families requiring symbolic evaluation): this endpoint returns **`202 Accepted`** instead of a synchronous verdict, because sandboxed symbolic evaluation cannot honestly fit the sub-150ms budget every other validation method holds to:
```json
// 202 response, CAS types only
{ "submission_id": "uuid", "status": "PENDING" }
```
Poll `GET /v1/submissions/:id` until it resolves to the same shape as the synchronous `200` response above. **Every non-CAS type stays fully synchronous** — check whether a type is CAS-backed before assuming which response shape you'll get; don't build a poll loop for everything by default.

`UNPARSEABLE` never increments `attempt_index` and never affects the student's mastery tracking — a malformed submission is not a wrong attempt.

## 3. Authentication — both are placeholders right now

Neither of these is production-ready. **Do not ship a delivery layer against either as-is:**
- `taskgen`'s webhook-secret check (`X-Webhook-Secret` / `TASKGEN_WEBHOOK_SECRET`) is a placeholder — real Telegram webhook-secret verification is a deployment prerequisite, not yet built.
- `grader`'s QR-token check (`X-QR-Token` presence only) is a placeholder — signed, scoped, time-boxed token verification is a deployment prerequisite, not yet built.

If you're building against a local/dev instance this doesn't block you; it blocks going further than that.

## 4. The `answer_widget` / `widget_config` contract

Every item's `answer_widget` selects a frontend affordance; it is not a new backend validation method. Render the control from `answer_widget` and its `widget_config`, then serialize the completed control into `raw_input` before calling `POST /v1/items/:id/submissions`.

This is **frontend-only**. The submission endpoint, request body, grader dispatch, and stored `SUBMISSION.raw_input` contract are unchanged. The eventual bot/web layer has zero backend work to coordinate for these widgets; it only has to emit the exact client-side serialization below.

### Widget kinds and exact serialization

| `answer_widget` | Expected UI pattern | Required `widget_config` | Exact `raw_input` serialization |
|---|---|---|---|
| `NUMERIC` | One numeric field/keypad. Permit the sign and decimal notation appropriate to the item. | `null` | Send the field's text value as one string, without adding a label or wrapper. Example: `743`. |
| `FRACTION` | Two numeric fields, numerator over denominator, with a visible `/`. | `null` | Join the two field values with one slash and no spaces: `numerator/denominator`. Example: `3/8`. |
| `CHOICE` | Tappable buttons; do not offer free text. | `{"choices":["<",">","="]}`. The list is authoritative and comes from the backend validator whitelist. | Send the tapped choice value verbatim, including its case/symbol form. Example: `=`. |
| `TUPLE_N` | The configured number of labeled fields, in declared order. | `{"field_count":2,"fields":[{"key":"field_1","label":"частное"},{"key":"field_2","label":"остаток"}]}`. | Join field values in order with a comma, with no brackets: `field_1,field_2`. Example: `8,5`. The shared parser also accepts legacy `;` and `ост.`/`остаток` separators, but clients should emit the comma-canonical form. |
| `SET_LIST` | Repeatable numeric fields with add/remove controls, capped by `max_items`. | `{"max_items":5,"item_label":"value"}`. | Join entered values with commas, with no brackets: `value_1,value_2,...`. Example: `-2,5`. The grader sorts members and rejects duplicates; the client should preserve entered values and not silently deduplicate them. |
| `MATRIX_GRID` | Numeric fields in a `rows × columns` grid, read left-to-right and top-to-bottom. | `{"rows":2,"columns":2,"cell_label":"entry"}`. | Serialize the grid as the existing nested JSON numeric-array format, preserving row-major order. Example for `[[1,2],[3,4]]`: `[[1,2],[3,4]]`. A scalar string is used only for a matrix type whose answer is a scalar determinant. |
| `STRUCTURED_CANON` | Small labeled form generated from the canonical template. | `{"template":"{a}√{b}"}` (or the type's actual template). | Substitute field values into the template exactly and send the resulting canonical string, with no UI labels or JSON wrapper. Example: `3√5`. |
| `EXPRESSION` | Free-text mathematical expression; symbol assistance and preview are optional UI conveniences. | `null` | Send the expression text exactly as entered; do not wrap it in JSON or add a widget prefix. |

`widget_config` is `null` only where the widget has no additional structure (`NUMERIC`, `FRACTION`, and `EXPRESSION`). A client must not invent missing choices, labels, dimensions, separators, or templates from `type_id`; use the metadata delivered with the item and the serialization rules above. If a requested rendering target is unavailable, that is a rendering decision (§5), not a reason to change `raw_input`.

## 5. Locale and rendering

- `locale` states the language the `problem` text is (or should be — see the active locale-content-correction work in `docs/srd/00-scope-lock.md`'s scope amendments before trusting every already-generated item's claimed locale blindly).
- `render_target: latex` items always have a `plaintext` (or `unicode-math`) sibling template available for the same `type_id`/locale — if your channel can't render LaTeX (e.g. a plain-text bot message), request/fall back to the non-LaTeX render target rather than showing raw LaTeX source to a student.

---

## 6. What this document deliberately does not decide

- Which channel(s) get built first, or at all (bot vs. web vs. print-first).
- How a printed worksheet is laid out or numbered beyond "the `items` array order is your numbering" (§2).
- Any native-mobile-specific input handling beyond the general widget contract in §4.
- Anything about `cas` or `analytics` beyond the CAS submission exception already noted in §2 — both remain gated per their own SRD status.

These are open design questions for whoever builds the delivery layer, not settled by this contract.
