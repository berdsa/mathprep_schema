**ADR-006 — Independent services in independent git repositories, integrated only through PostgreSQL** *(new this pass)*
Status: Accepted. Context: direct operator instruction; supersedes ADR-001/CON-03. Options considered: (a) modular monolith (ADR-001's choice) — rejected, contradicts the explicit new instruction; (b) N independent services communicating over HTTP/RPC to each other — rejected, would require a service-discovery/networking layer the "go, postgres" stack line doesn't call for, and none of the described workflow ("takes tasks from db... writes into db") implies direct service-to-service calls; (c) N independent services integrated *only* through the shared Postgres schema (job-queue tables, `SKIP LOCKED` polling) — **accepted**, matches both the literal stack constraint and the literal described data flow. Consequences: **+** genuine fault isolation and independently-deployable, independently-owned codebases (a `grader` bug can't corrupt `taskgen`'s state); **+** narrower DB roles per service (see `04-nfr-risk-ops.md` STRIDE update) is a real security improvement over the old single-role monolith; **−** loses the old ADR-001's "single deploy artifact" simplicity — three CI pipelines, three sets of ops runbooks, three places a version can drift; **−** requires the disclosed `schema` shared-module exception (ADR-007) to avoid enum/schema drift, which is itself a small, ongoing coordination cost. Reversal cost: MEDIUM — merging three repos back into one is more work than the original monolith→split move, since each will have accumulated its own CI config, its own versioning, its own release history. Revisit trigger: if the coordination overhead of keeping `schema` versions in sync across services becomes the dominant source of bugs (tracked via RISK-005).

**ADR-007 — A minimal shared `schema` Go module is the one disclosed exception to "no shared code between services"** *(new this pass)*
Status: Accepted. Context: ADR-006 forbids business-logic sharing between services, but the cartridge's own quality-gate rule (REF-02: "normalize once in a shared layer... or CANON/SET rules will drift") is a direct, load-bearing constraint that a hard "zero shared code" reading would violate. Options: (a) zero shared code, each service hand-copies enums and the validation pipeline — rejected, reintroduces exactly the drift risk REF-02 warns against, and violates NFR-006 (golden-test regression) the moment the two copies diverge; (b) a shared *runtime* library loaded by both services at startup from a common location — rejected, reintroduces a hidden coupling closer to the monolith ADR-006 just rejected; (c) a versioned Go module, `schema`, containing only DDL migrations, dictionary constants, row structs, and the validation-pipeline package, consumed via normal `go.mod` dependency pinning — **accepted**. Consequences: **+** one place normalization logic and enums live, migration effort is not duplicated; **−** a version bump in `schema` requires a coordinated (though not simultaneous) upgrade in each consumer, tracked as RISK-005. This ADR is the disclosed boundary of "independent services" — named explicitly here so the operator can veto it if the intent was zero shared code even in this narrow contract-only form.
